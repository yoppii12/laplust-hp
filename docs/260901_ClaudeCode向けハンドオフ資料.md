## 1. プロジェクトの背景

- 現在、株式会社LAplustのコーポレートサイト（`laplust.com`）はStudio.Design上で構築・運用されている
- 移行の動機は以下の5点（依頼者の原文ベース）
  1. Studioが独自基盤上で動作しており、コーディングエージェント（Claude Code等）との連携によるコード編集・改善が行えない
  2. Claude等と連携し、HPの改善を継続的かつ迅速に進めたい
  3. GA4等を活用して改善指標を洗い出し、再帰的に改善できる状態にしたい
  4. ニュースリリース等の発行時に、Studio独自のCMS専用UIを都度操作する煩わしさを解消したい（CMSの「入稿」機能自体は必要）
  5. プロンプトベースでスピーディに改善を行いたい

### 重要な前提（繰り返し強調）
StudioはHP全体を丸ごとエクスポートする機能を持たない。したがって本プロジェクトは「移行」ではなく、**現行サイトを参照した実質的な「再構築」**である。ゴールは「Studioの内部コードを流用すること」ではなく、「利用者から見て区別できないレベルで見た目・挙動・コンテンツを再現すること」。

## 2. 確定した技術スタックと結論

| 区分 | 結論 | 補足 |
|---|---|---|
| フロントエンド | Next.js（静的出力中心。SSR/ISRに依存しない） | コーディングエージェントとの相性を最優先した選定 |
| コンテンツ管理 | Markdown＋Git（frontmatter形式）。SaaS型CMS（microCMS/Notion API）は不採用 | 更新頻度（月数本）を踏まえるとSaaS CMSはオーバースペックと判断 |
| ホスティング（先行） | **Netlify** | 保守工数は社内で対応可能なので本来VPSとほぼ互角だが、まずインフラ変数を減らして「コンテンツ・運用フローの検証」に集中するため先行導入 |
| ホスティング（将来検討） | さくらのVPS等 | 静的出力構成を維持している限り移行コストは低い。コスト最小化・データ自社管理を重視する場合に検討 |
| 計測 | GA4／GTM／Google Search Console | 10章の改善サイクルの基盤 |
| 可視化 | **Looker Studio**（GA4データを可視化） | 現行Studioの簡易アナリティクス画面（サイト全体Visitor数・ページ別ランキング・期間比較）の代替。再帰的改善サイクルの起点 |
| AIデモ連携 | AWS上のAPIをブラウザから直接呼び出し | CORS設定・APIキー公開範囲の設計が必要（未決） |
| 動画配信 | AWS S3＋CloudFront、または YouTube限定公開 | サイト本体・GitHubには動画を置かない（詳細は4章） |
| 問い合わせフォーム | Netlify Functions → Google Sheets API → GWS上のスプレッドシート | Netlify Forms（Netlify純正のフォーム機能）ではない点に注意。詳細は5章 |
| ドメイン | 既存ドメイン（laplust.com）を継続利用 | SEO評価維持のため変更しない |

## 3. なぜその結論に至ったか（検討過程の詳細）

### 3-1. Studioの独自基盤について
- Studio.Designは独自の内部基盤で構築されており、フルエクスポート機能を持たない
- 2026年6月11日以降、Studioの新規プロジェクトはサーバー側でHTMLを完成させる新基盤に刷新されているが、**laplust.comは既存プロジェクトのため旧基盤（クライアントサイドレンダリング）のままである可能性が高い**。実際、`web_fetch`でlaplust.comを取得するとメタ情報（title/OGP等）しか取れず、本文コンテンツは一切取得できなかった（JavaScript実行後でないと描画されないため）。→ Claude Codeが現行サイトの内容を機械的に読み取る際は、**単純なHTTP取得では不十分。ヘッドレスブラウザ（Playwright等）でJS実行後のDOMを取得する必要がある**。

### 3-2. SEOに関する整理
- StudioのSEO機能（title/meta/OGP設定、XMLサイトマップ自動生成、301リダイレクト、GA4/GTM/Search Console連携）は2026年時点でかなり充実しており、「StudioだからSEOに弱い」という単純な話ではない
- ただし移行に伴うURL変更のリダイレクト設計は必須（9章参照）
- 結論：SEOを理由に移行するのではなく、開発体験・改善サイクルの速さを理由に移行し、SEO面は移行時の丁寧なリダイレクト設計で現状維持を狙う

### 3-3. CMSの要否について
- 当初はmicroCMSまたはNotion APIをヘッドレスCMSとして使う案を検討した
- しかし「CMSの役割は記事投稿UIだけではない」ことを整理した上で、御社の更新頻度（月数本のニュースリリース）を踏まえ、**SaaS型CMSは不要と判断**
- 最終的に「Markdownファイルをリポジトリに追加してgit push」するだけで完結する運用に決定。Claude Codeが記事作成〜pushまでを代行する想定
- CMSを導入する場合の判断基準（将来の再検討ポイント）：更新者が多数・頻度も高い・承認フローが必要になった場合のみ、この段階で初めてSaaS型CMS導入の価値が出る

### 3-4. ホスティング選定（Netlify vs Vercel vs さくらVPS）の経緯
- 当初はNext.js開発元であるVercelを軸に検討していたが、依頼者が既にNetlifyでのデプロイ実績（兵庫県セミナー用HTML）を持っていたため、Netlifyも比較対象に追加
- Vercel/Netlifyの技術的な優劣は僅差（Next.js最新機能への対応速度はVercelがやや速いが、Netlifyも主要機能はサポート済み）。料金体系は2025〜2026年にかけて変動が大きく情報源によって数字が食い違うため、契約直前に最新料金ページを確認することを推奨
- 「自社サーバー（さくらVPS）で運用したい」という当初案も検討したが、以下の理由でいったんNetlify先行に決定：
  - 静的サイト中心の構成なら、VPSは「git push→自動デプロイ」「SSL自動更新」「プレビューデプロイ」等、Netlifyが標準で持つ機能を自作する必要が生じる
  - 依頼者から「インフラ運用の経験は豊富で保守工数はネックにならない」との発言があり、判断基準が「保守工数」から「コスト最小化／データ自社管理をどこまで重視するか」という好みの問題に変化した
  - 結論：Netlifyで先に構築・検証し（インフラ変数を減らしてコンテンツ運用フローの検証に集中）、静的出力を維持する限り移行コストは低いため、VPS移行は後から判断すればよい

### 3-5. AIデモ機能・動画配信について
- LAplustが構築したAI関連サービスのデモをサイトに設置する予定。UIはサイト内、実処理はAWS上のAPI呼び出し
- この構成はブラウザからのfetchで完結するため、ホスティング先（Netlify/VPSどちら）を選んでも判断に影響しない。CORS設定とAPIキーの公開範囲設計だけが必要（未決事項）
- 動画については、GitHubでの管理可否を検討した結果、**GitHubは技術的に大容量ファイルを保存できても配信には向かない**（Git LFSはCDN機能を持たない）と判断。AWS S3＋CloudFront、またはYouTube限定公開を採用

### 3-6. 現行サイトの動画アセット調査（実際に確認した生データ）
依頼者が開発者ツールでlaplust.comのファーストビュー要素を確認し、以下のHTMLが得られた。

```html
<video data-s-bf04ceaa-b5a9-4bac-8a08-08bea3f565ef="" autoplay="" controls="" playsinline="true" class="video sd"
  src="https://storage.googleapis.com/studio-design-asset-files/projects/NxqgdRVEa1/s-1920x1080_170574dd-7d9a-42c5-b72e-abd60b427eac.mp4#t=0.01"></video>

<img data-s-555b2f24-2277-4aba-b793-1fa205dca4d7="" class="sd" alt=""
  src="https://storage.googleapis.com/studio-design-asset-files/projects/NxqgdRVEa1/s-28x25_webp_baa795dc-01be-459e-92dd-b60493432a58.webp">
```

**分かったこと：**
- ファーストビューはGIFではなくMP4動画（`<video>`タグ）
- 動画・画像の配信元はStudio独自のホスティングではなく、**Google Cloud Storage**（`storage.googleapis.com/studio-design-asset-files/`）のバケット
- URLパターン：`https://storage.googleapis.com/studio-design-asset-files/projects/{プロジェクトID}/{ファイル名}`
- **本プロジェクトのStudioプロジェクトID：`NxqgdRVEa1`**（Studioのダッシュボードのアナリティクス画面URL `app.studio.design/projects/NxqgdRVEa1/dashboard/analytics` からも同一IDが確認できる）
- このURLパターンが分かっているため、**サイト全体をヘッドレスブラウザで巡回し、`storage.googleapis.com/studio-design-asset-files/projects/NxqgdRVEa1/` 配下のURLをDOMから自動抽出すれば、動画・画像アセットを機械的に洗い出し・ダウンロードできる見込みが高い**
- これはStudioの「動画アップロード機能」（1ファイル最大1GB、mp4/webm対応）の実体であり、YouTube/Vimeo埋め込みではない

**Claude Codeへの依頼事項（自動化フロー）：**
1. 現行サイトの各ページのHTMLを取得し、`<video>`/`<img>`タグのsrc属性から`storage.googleapis.com`配下のアセットURLを自動抽出する
2. 抽出したURL一覧をもとに、動画・画像ファイルを一括ダウンロードする
3. ダウンロードしたファイルをAWS S3の所定バケットへアップロードし、CloudFront経由のURLに置き換えた対応表（旧URL→新URL）を生成する
4. Next.js側のコンテンツ（Markdown／コンポーネント）内の参照URLを、生成した対応表に基づき一括置換する

### 3-7. デザイン・コンテンツの再現方針（重要・依頼者の強い要望）
依頼者から「現在Studio上で動いているデザインやコンテンツやフォームなどの構成は完全一致させたい」「Claudeにコンテンツの抽出やデザインの模倣は全てやってもらいたい」という明確な要望があった。

**方針：**
- 再構築後のサイトは、現行Studioサイトのデザイン・コンテンツ・フォーム構成と、利用者から見て区別できないレベルで一致させることを目標とする
- 実現方法：
  1. Claude Codeがヘッドレスブラウザ（Playwright等）を用いて現行サイトの全ページをJavaScript実行後の状態で自動巡回する
  2. 各ページのDOM構造・テキストコンテンツ・CSSスタイル（配色・フォント・余白等）・画像／動画／フォームの構成を機械的に抽出する（3-6節の手法をサイト全体に拡張）
  3. 抽出した内容をもとに、同等の見た目・挙動をNext.js（React）コンポーネントとして再構築する
  4. 問い合わせフォームについても、現行の入力項目・必須／任意の区別・エラー表示・送信後の挙動を抽出し、4章で決定したGoogle Sheets連携の裏側と組み合わせて再現する
  5. 新旧サイトのスクリーンショットを比較するビジュアルQAを実施し、デザインのズレを検出・修正する

### 3-8. 問い合わせフォーム・管理機能の検討経緯
- 現行Studioには問い合わせフォームの送信内容（氏名・メールアドレス等）を管理画面で一覧確認できる機能がある。再構築後も同等機能が必要
- 個人情報（氏名・メールアドレス）を扱うため、保存先・アクセス権限の設計を慎重に検討した
- 検討した3方式：
  1. **Netlify Forms**（Netlify標準機能）：開発工数ほぼゼロだが、専用の管理画面は作れず、データはNetlify（米国）に保存される
  2. **Google Sheets連携**：フォーム送信をGoogle Sheets APIでGWS上のスプレッドシートへ書き込み、一覧管理する
  3. **フル自社開発**：専用DB＋認証付き管理画面をvibe codingで自作。自由度は最も高いが開発工数も最大
- **依頼者の選択：②Google Sheets連携**。理由は、LAplustがGoogle Workspaceをマスターデータとして運用する方針をすでに進めており、閲覧権限も既存のGWSアカウント権限管理でそのまま担保できるため
- 実装方針：
  - サイト上の問い合わせフォームからの送信を、**Netlify Functions**（サーバーレス関数）で受け取る
  - Netlify Functionsが受け取った送信内容を、Google Sheets APIを用いてGWS上の指定スプレッドシートへ1行として追記する
  - 問い合わせ担当者は当該スプレッドシートを閲覧・管理する（新規の管理画面は開発しない）
  - スパム対策として、フォームにhoneypot項目またはreCAPTCHAを設置する
  - 個人情報を扱うため、保存期間・削除ルールは運用フェーズで別途取り決める（未決）

**重要な技術的注意点（依頼者から明確な確認あり）：**
- フォームの**見た目（UI）は完全に自由**。Netlifyに依存するのは「送信後の裏側の処理（Netlify Functions）」だけであり、HTML/CSS/入力項目のデザインには一切制約がない
- 「Netlify Forms」（Netlify純正のフォーム保存機能）と「Netlify Functions」（汎用サーバーレス関数）は別物。今回採用したのは後者
- GA4のトラッキングタグと異なり、この仕組みは**Netlify Functionsというホスティング先固有の機能に依存している**。将来さくらVPS等へ移行する場合、Google Sheets APIへの書き込みロジック自体は再利用可能だが、フォーム送信を受け取る入り口（サーバーレス関数の部分）はVPS上の小規模なAPIエンドポイントとして作り直す必要がある

### 3-9. GA4駆動の改善サイクルとLooker Studioの位置づけ
- 依頼者から「（Looker Studioは）再帰的な改善の根幹をなす部分だと思う」と明確な位置づけの発言があった。単なる計測ツールの追加ではなく、**改善サイクル全体の起点**として扱うこと
- Looker Studio（旧Googleデータポータル）はGoogleの無料BIツール。GA4を接続するだけで、現行Studioの簡易アナリティクス画面（サイト全体Visitor数推移、ページ別Visitor数ランキング、期間比較インサイト）と同等以上のダッシュボードをノーコードで再現できる
- GA4のトラッキングタグはページに埋め込むJSタグのみで完結するため、**ホスティング先（Netlify/VPS）に依存しない**（問い合わせフォームとの対比で重要な違い）
- 想定する改善サイクル：
  1. 週次または月次で、Looker Studioダッシュボードの数値（の要約）をClaude Codeに共有する
  2. Claude Codeが数値の変化点（急落・急伸したページ、直帰率の悪化等）を分析し、具体的な改善案を提示する
  3. 承認された改善案をClaude CodeがGitHubへ実装し、Netlifyが自動反映する
  4. 反映後の数値をLooker Studioで再度観測し、次のサイクルへつなげる
- 将来的にGoogle Analytics Data APIを用いてClaude Code側から直接データを取得する自動レポーティングへ発展させる余地あり（まずは目視共有ベースで運用開始）

## 6. 社内の運用ルール（成果物作成時に遵守すること）

- 出力するファイル名には日付情報を含める。命名規則は `yymmdd_(資料名)`
- 出力するファイル名称に「LAplust」は含めない
- 出力ファイルのコンテンツには以下のデザインルールを適用する
  - `#FFFFFF`：ベースカラー
  - `#171A31`：メインカラー
  - `#F05A22`：アクセントカラー（1ファイル中で3%未満の使用に留める）
